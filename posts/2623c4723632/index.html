JS 原生事件和 React 合成事件

发表于 2026-07-02 分类于 笔记 ， 前端

捕获这一块，冒泡这一块

JS 原生事件

相关方法

  1. event.preventDefault: 阻止事件默认行为
  2. event.stopPropagation: 仅阻止事件继续传播
  3. event.stopImmediatePropagation: 阻止事件继续传播，并且阻止目标元素上绑定的其他 同类型 事件的事件监听函数的执行。

React 合成事件

事件委托

我们在 React 的 JSX 上绑定事件时，其实并非直接在相应元素上进行操作。
React → <button onClick={onClick} ≠ <button onclick='onclick()' ← 原生 JS

尝试给按钮绑定一个事件，并通过控制台看看实际情况：

可以发现在 button 上其实只放了一个占位的空函数，里面什么也没有做。

实际上，绝大部分监听事件是在根节点进行绑定的并处理的。

这种做法就是事件委托，是一种利用事件冒泡机制，将子级的事件向上传递，最终交给父级统一处理的设计模式。

React 事件机制简介

React 自己实现了实现了包括 代理、注册监听、构造合成事件、分发事件 等一整套事件流管理系统。而我们代码中能直接接触到的实际上是 React 给我们包装好的合成事件

  • 事件监听绑定

  • 处理合成事件
  • 收集事件响应链路
  • 触发事件回调函数

合成事件的优点如下：

  1. 一致性：React 统一对事件进行代理、注册、分发，抹平了不同浏览器之间的底层差异

  2. 可拓展性：React 在原有基础上进行改造，实现了自己的一些事件，更好地与 useState 等状态进行联动

    • 比如 <input type="checkbox" /> 和 <input type="radio" />，change 事件触发时机是比较怪异的，React 做了新的 onChange 来统一

  3. 提高效率（性能）：事件委托的设计就是用于解决事件处理程序过多的问题

    • 由于每绑定一个事件都会增加内存使用，使用事件委托，只需在 DOM 树中尽量最高的层次上添加一个事件处理程序；这减少了增删 DOM 元素时事件的添加移除动作，以此减少资源消耗；
    • 统一进行回调函数的处理，React 可以批量执行事件的具体回调函数，达到节约性能的目的。

React 混合使用合成事件和原生事件

以下的测试均基于 React 17。React 17 后，几乎将所有的事件委托到根节点进行处理分发，根据实际触发的 DOM 节点链路按顺序组装一系列的回调函数，然后放到队列里去执行。

开发过程中，有时候不可避免需要混合使用两种事件，我们需要注意它们执行的时机和可能存在的互相影响。以下是两个常见问题：

1. 合成事件和原生事件的回调执行先后顺序？

分别给 document， wrapper-div，button 绑定 click 合成事件和原生事件，点击后控制台输出如下：

  1. 从 document 开始执行捕获回调；
  2. 在 root 处，根据触发顺序，依次执行 div 和 button 的合成事件的捕获回调，然后继续向下传播；
  3. 依次触发 div，button 原生事件的捕获回调；
  4. 依次触发 button，div 原生事件的冒泡回调；
  5. 回到 root，依次触发合成事件的冒泡回调；
  6. 最后执行 document 的冒泡回调并结束。

2. 混用事件的情况下如何阻止事件传播？

对于原生 JS 事件，我们可用 event.stopPropagation、event.stopImmediatePropagation 来阻止当前事件继续传播或同时阻止该元素上其它同类回调的执行

但在 React 里，由于不同种事件的回调执行先后问题，某些情况下是不适用的。

场景： 父组件通过原生方式做了监听，在子组件添加有同样类型的监听事件，现在想在子组件覆盖父组件的动作

思考：为什么需要 event.nativeEvent？

子组件的回调分别使用 event.stopPropagation、event.nativeEvent.stopImmediatePropagation，发现并不能成功阻止。

原因很简单，在合成事件的回调执行前，原生事件回调已经结束了
上述的两个方法只能阻止事件继续传播，对于在此之前已经触发的回调是无能为力的

解法1： 在不改变父组件的情况下，使用 onXXXCapture；但也要考虑执行回调提前带来的其它问题，比如是否会和其它回调冲突等
解法2： 也用原生事件去处理子组件的回调；但这会导致整个 React 组件的事件回调执行混乱，尽量避免

React 16 / React 17+ 事件机制的差异

在 React 16，是将事件委托节点绑定在 document 上的，合成事件的执行时机和绑定在 root 上不同；

  1. 所有的合成事件（无论捕获还是冒泡）都在 document 的冒泡阶段统一执行，这就导致在合成事件的回调中，基本不可能去阻止原生回调的执行。一旦引入某些外部组件用了原生监听，而又要自定义的话，只能在 React 组件中用原生监听拦截。
  2. 不是全部事件都能绑定到 document，比如 audio、video 标签的 onplay、onpause 等，因为这些标签的事件不会冒泡；

总结

  1. React 使用事件委托机制统一处理所有事件监听，委托的节点是 root (17+) 或 document (16)
  2. React 合成事件和原生事件回调执行顺序：

React 17 后，除了 document，合成事件的捕获回调总在原生事件前，冒泡回调总在原生事件后；

React 16，除了 document，合成事件回调总在原生事件后。
